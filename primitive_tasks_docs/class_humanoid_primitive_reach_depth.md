## Task summary

This task uses the same humanoid base environment as the other primitive tasks, but adds:

- a kinematic red sphere target
- a base-mounted depth camera
- a right-arm-only action space
- a processed depth-derived command in the policy observation

There is no explicit success flag and no success termination. Reaching quality is encoded through reward terms only.

## Observation space

The shared primitive observation block is still present, and the task adds one processed depth term.

| Term | Shape in code | Actual content | Noise / processing |
| --- | --- | --- | --- |
| `base_lin_vel` | 3 | Root linear velocity | Uniform additive noise in `[-0.05, 0.05]` |
| `base_ang_vel` | 3 | Root angular velocity | Uniform additive noise in `[-0.05, 0.05]` |
| `base_rpy` | 3 | Root roll, pitch, yaw | Uniform additive noise in `[-0.02, 0.02]` |
| `joint_pos` | all robot joints | Joint positions relative to default, with semantic sign conversion for right-side joints | Uniform additive noise in `[-0.01, 0.01]` |
| `joint_vel` | all robot joints | Joint velocities relative to default, with the same semantic sign conversion | Uniform additive noise in `[-0.15, 0.15]` |
| `foot_contacts` | 2 | Binary left/right foot contacts | Threshold `1.0` |
| `actions` | 5 | Last raw right-arm action | No extra noise |
| `target_pos_base_from_depth` | 3 | Smoothed target-position estimate derived from the depth image | No extra noise after estimation |

Important implementation detail:

- The policy does **not** receive the raw `64 x 64` depth image.
- The policy receives only a 3D estimate generated by `DepthTargetPosCommand`.
- The reward uses the ground-truth target object position in world coordinates, not the depth estimate.

## How the depth estimate is actually computed

The `DepthTargetPosCommand` updates a 3D estimate every step:

1. It reads `distance_to_image_plane` from the depth camera.
2. It marks pixels valid if they are finite and greater than `min_depth = 0.20`.
3. It finds the nearest valid depth pixel.
4. It clamps that depth to `[0.20, 2.00]`.
5. It converts pixel coordinates into a coarse base-frame estimate with:
   - `x = depth`
   - `y = -u_norm * depth`
   - `z = -v_norm * depth`
6. It replaces non-finite estimates with zero.
7. It exponentially smooths the command with `smooth_factor = 0.75`:
   - `new_command = 0.75 * old_command + 0.25 * new_estimate`

The command config also sets `resampling_time_range = (0.5, 0.5)`, but `_update_command()` is still called every step, so the estimate is not only updated at 0.5-second intervals.

The command term exposes one metric:

- `depth_target_norm = norm(estimated_target_pos_base)`

## Action space

This task overrides the default whole-body primitive action and uses right-arm-only joint position control.

| Item | Implemented behavior |
| --- | --- |
| Action type | `JointPositionActionCfg` |
| Controlled joints | `Right_Shoulder_Pitch_RS03`, `Right_Shoulder_Roll_RS03`, `Right_Shoulder_Yaw_RS02`, `Right_Elbow_RS02`, `Right_Wrist_RS00` |
| Action dimension | 5 |
| Scale | `0.35` |
| Offset | Default joint positions from the articulation asset (`use_default_offset=True`) |
| Applied command | `processed_action = default_joint_pos + 0.35 * raw_action`, then `set_joint_position_target(...)` |
| Lower-body control | Not commanded directly by this task-specific action term |
| Torque control | Not used |

## Reward function

### Shared stability and smoothness terms

| Reward term | Weight | Actual computation |
| --- | --- | --- |
| `termination_penalty` | `-100.0` | Applies on non-timeout terminations only |
| `torso_tilt_l2` | `-2.0` | Sum of squared projected-gravity XY components |
| `action_rate_l2` | `-0.01` | Squared action change between consecutive steps |
| `joint_vel_l2` | `-2.0e-4` | Sum of squared joint velocities over the articulation |

### Reach-specific terms

| Reward term | Weight | Actual computation |
| --- | --- | --- |
| `reach_target` | `+8.0` | `1 - tanh(distance / 0.05)`, where distance is the world-frame distance between `Wrist_Right_1` and the target center |
| `arm_joint_deviation` | `-0.1` | Sum of absolute deviation from default on the 5 controlled right-arm joints |
| `undesired_contacts` | `-0.5` | Counts monitored body groups whose contact force exceeds `1.0` |

Bodies monitored by `undesired_contacts`:

- `base_link`
- `Head_1`
- `Hip_1`
- `HipYoke_.*`
- `UpperThigh_.*`
- `LowerThigh_.*`
- `Shin_.*`

Because the target sphere has collision disabled, the task does not use target contact as a success event or reward input.

## Success criteria

No explicit success criterion is implemented.

What the current code rewards instead:

- Small distance between the right wrist and the target center
- Small right-arm deviation from the default posture
- Fewer undesired contacts on the monitored body set

There is no reach-threshold success event such as "distance below X for Y frames."

## Failure conditions

| Condition | Implemented rule |
| --- | --- |
| Timeout | Episode ends at `8.0 s` |
| Bad orientation | Root orientation fails when the gravity-alignment angle exceeds `0.8 rad` |
| Root too low | Root height below `0.55 m` |
| Base contact | Disabled |

The `undesired_contacts` term is a reward penalty only. It does not terminate the episode.

## Reset conditions

Episodes reset when a termination or timeout occurs.

### Robot reset

| Reset component | Implemented behavior |
| --- | --- |
| Robot root position | Default root position plus sampled offsets: `x in [-0.10, 0.10]`, `y in [-0.10, 0.10]`, `z in [0.05, 0.10]` |
| Robot root orientation | Additional yaw sampled in `[-0.20, 0.20]` |
| Robot root velocity | All components reset to zero |
| Joint positions | Reset exactly to default joint positions |
| Joint velocities | Reset exactly to zero |

Because `CLASS_HUMANOID_CFG` sets the default root position to `(0.0, 0.0, 0.8)`, the actual robot reset height is `0.85` to `0.90` meters above each environment origin.

### Target reset

The task adds a `reset_target` event that calls `reset_root_state_uniform(...)` on the target asset.

Configured sampled offsets passed into that helper:

| Axis | Configured sampled range |
| --- | --- |
| `x` | `[0.45, 0.70]` |
| `y` | `[-0.22, 0.22]` |
| `z` | `[0.82, 1.02]` |
| velocities | all zero |

Important implementation detail:

- `reset_root_state_uniform(...)` adds sampled offsets to the asset default root state.
- The target default root state is already `(0.55, 0.0, 0.95)`.

So the actual reset target position relative to each environment origin is:

- `x in [1.00, 1.25]`
- `y in [-0.22, 0.22]`
- `z in [1.77, 1.97]`

That is the behavior implemented by the current code path, even though the surrounding comment says the target is randomized "in front of the robot."

## Evaluation metrics actually exposed by code

Explicit task-specific metric defined in the command term:

- `depth_target_norm`

Useful quantities computed in helper functions but not explicitly registered as standalone metrics in the environment config:

- end-effector to target distance
- target position in base frame from ground truth
- target position in base frame from depth

Not implemented:

- No success counter
- No success-rate evaluator
- No target-reached termination
